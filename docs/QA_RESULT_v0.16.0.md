- **대상 버전**: `v0.16.0`(하네스) / 실행 시점 `v0.16.1`
- **범위**: `./gradlew evalAgent` — 에이전트가 **어떤 상태에서 어떤 도구를 골랐는가**를 실제 모델로 측정
- **모델**: `qwen/qwen3.7-plus`
- **환경**: 로컬 Windows(Git Bash), 기본 프로필(인메모리 저장소)
- **실행**: 기저 3회(16케이스 × 3·3·5회 = **176회**, 구 프롬프트) + 검증 1회(17케이스 × 20회 = **340회**, v0.16.2 프롬프트) = **516회**
- **관련 문서**: [EVAL.md](EVAL.md) · [AGENT.md](AGENT.md) · [QA_CHECKLIST.md](QA_CHECKLIST.md) F-25

> **왜 세 번인가** — 1차는 Windows 콘솔 코드페이지 때문에 리포트 한글이 깨져 화면으로만 부분

> 스크린샷으로 읽어낸 값만 기록합니다. 3차는 반복을 5회로 올려 돌린 실행입니다.
>
> **결과적으로 이 반복이 결론을 세 번 바꿨습니다** — 2차는 "실패가 케이스를 옮겨 다닌다"를,
> 3차는 "기저 실패율이 예상의 절반이다"를, 4차(340회)는 **"모델이 막힌 수정을 이월로 대체한다"**를

### 3차 실행이 바꾼 결론 — 기저 실패율이 생각보다 낮다

3차는 반복을 5회로 올렸는데 **`notool.*`가 10회 모두 통과**했습니다. 세 실행을 합치면:

| | `notool.*` 실행 | 실패 |
| :--- | ---: | ---: |
| 1차 (×3) | 6 | 1 |
| 2차 (×3) | 6 | 1 |
| 3차 (×5) | 10 | 0 |
| **합계** | **22** | **2 (9.1%)** |

앞선 두 실행에서 "6회 중 1회(17%)"로 보였던 것이 **표본이 작아 과대평가**된 값이었습니다. 실제
기저 실패율은 약 9%입니다.

**이 숫자가 검증 계획을 바꿉니다.** 실패율 9%면 `repeats=5`(= `notool` 10회) 실행에서 개선이
전혀 없어도 0회 실패가 나올 확률이 **39%**입니다. 즉 `repeats=5` 한 번으로는 v0.16.2 프롬프트
조정의 효과를 **판정할 수 없습니다** — 통과해도 개선인지 운인지 구분되지 않습니다.

그래서 v0.16.2에 **축 선택 옵션(`-Deval.only=`)** 을 넣었습니다. 이미 안정적인 14케이스까지 반복할
필요 없이, 흔들리는 축만 깊게 재기 위한 것입니다(8절 참고).

## 3. 유일한 실패 — 케이스가 아니라 모델의 성향

| 케이스 | 1차 | 2차 | 3차 |
| :--- | :---: | :---: | :---: |
| `notool.greeting`("안녕!") | ❌ 2/3 | ✅ 3/3 | ✅ 5/5 |
| `notool.thanks`("고마워!") | ✅ 3/3 | ❌ 2/3 | ✅ 5/5 |

**실패가 케이스 사이를 옮겨 다니다 3차에서는 아예 나타나지 않았습니다.** 1차만 봤다면
"`notool.greeting`이라는 케이스에 문제가 있나?"로 읽었을 텐데, 이동이 그 해석을 배제하고, 3차의
미재현이 **"드물게 일어나는 성향"**이라는 해석을 확정합니다 — 22회 중 2회(9%)입니다.

- 케이스를 다듬을 사안이 **아닙니다** → 시스템 프롬프트로 줄일 사안입니다(v0.16.2에서 조정).
- `-Deval.repeats=1`이었다면 이 구분을 못 했습니다. 반복 실행이 값을 낸 첫 사례입니다.
- 권한 위반이 아니므로 빌드를 깨지 않습니다. 비용은 늘지만(3왕복 → 4왕복) 설계는 온전합니다.
- **다만 9%는 검증을 어렵게 만듭니다.** 개선을 확인하려면 이 축만 깊게 반복해야 합니다 → 8절.

## 4. 재현되지 않은 것 — 비용 이상치

1차에서 가장 비쌌던 케이스가 2차에서 **가장 싼 케이스**가 됐습니다.

반복당 왕복 수로 환산해 비교합니다(3차는 5회 실행이라 총합을 그대로 비교할 수 없습니다).

| 케이스 | 1차 (÷3) | 2차 (÷3) | 3차 (÷5) |
| :--- | ---: | ---: | ---: |
| `write.update.completed_blocked` | **2.3왕복** | 1.0왕복 | 1.4왕복 |
| `write.update.confirmed_blocked` | 1.7왕복 | 1.0왕복 | 1.0왕복 |

1차에서는 수정 도구를 못 찾은 모델이 읽기 도구를 반복 호출하며 배회했는데(케이스당 7왕복·11,785
토큰), 2차·3차에서는 대체로 바로 "할 수 없다"고 답했습니다. **1회 실행의 비용 이상치를 구조적
문제로 읽으면 안 된다**는 사례입니다 — 비용 열도 정확도 열과 똑같이 반복해서 봐야 합니다.

3차에서 `write.update.draft`가 12왕복(2.4/회)으로 가장 비쌌는데, 일부 회차가
`get_today_tasks → update_plan_tasks → get_today_tasks`로 **수정 후 재확인**을 했습니다. 정답이고
막을 이유도 없지만, 이런 패턴이 늘면 비용이 배로 뜁니다 — 정확도 열만으로는 안 보이는 종류입니다.

## 6. 비용 특성 (3차 실행)

| 항목 | 값 |
| :--- | :--- |
| 80회 총합 | 231,040토큰 · $0.0818 |
| 실행당 | 2,888토큰 · $0.00102 · **1.79왕복** |
| 입력:출력 | 222,835 : 8,205 = **약 27:1** |

실행당 왕복이 1차·2차의 1.8과 사실상 동일합니다(1.83 → 1.77 → 1.79). **정확도보다 비용 쪽이 더
안정적**이라는 뜻이고, 그래서 왕복 수가 회귀 지표로 쓸 만합니다 — 프롬프트를 고쳤을 때 정확도는
잡음에 묻혀도 왕복 수의 변화는 바로 보입니다.

27:1은 **에이전트 루프의 구조가 그대로 드러난 숫자**입니다. 턴마다 직전 도구 결과가 붙은 대화
전체를 재전송하므로 입력이 누적으로 늘고, 출력은 도구 호출 한 줄이거나 짧은 답변입니다. v0.15.2의
사용량 계측이 없었다면 이 비율을 몰랐습니다.

## 8. 4차 실행 — v0.16.2 프롬프트 조정의 판정 (17케이스 × 20회 = 340회)

- **코드**: v0.16.3 (프롬프트 조정 + `only` 옵션 + 계획 정리 수정 포함)
- **결과**: 통과율 **99%**(338/340) · 업스트림 604왕복 · 1,016,562토큰 · **$0.3538** · 순차 약 80분
- 전체 케이스를 돌렸습니다(`only` 미사용). 340회가 완주한 것 자체가 v0.16.3의 계획 정리가 필요했고
  작동한다는 증거입니다 — **구 코드라면 201번째에서 죽습니다**(한도 200).

### 판정: 개선 미확인 (기준 미달)

미리 정한 기준은 **"`notool.*` 40회에서 실패 0~1이면 개선"**이었습니다.

| | 기저(구 프롬프트) | 4차(신 프롬프트) |
| :--- | :--- | :--- |
| `notool.*` 실패 | 2 / 22 = 9.1% | **2 / 40 = 5.0%** |
| 기저 가정하의 기대 실패 | — | 3.6회 |
| p-value | — | **0.283** |

**기준을 사후에 바꾸지 않습니다.** 실패 2회는 기준 미달이고, p=0.283은 개선의 근거가 못 됩니다.
5%와 9%는 이 표본에서 구분되지 않습니다.

**되돌리지는 않습니다** — `read.today.after_greeting`이 **20/20**으로 "질문이 섞이면 질문이 이긴다"가
확실히 작동합니다. 억제 과잉은 없고, 규칙 자체는 해롭지 않습니다.

케이스를 갈라 보니 원인이 보입니다:

| 케이스 | 누적 실패율 | 해석 |
| :--- | ---: | :--- |
| `notool.greeting` ("안녕하세요!") | **3/31 = 9.7%** | 인사는 대화를 **여는** 말 → 모델이 "인사 + 브리핑"을 자연스러운 응대로 본다 |
| `notool.thanks` ("고마워요…") | 1/31 = 3.2% | 감사는 대화의 끝 → 후속 행동이 필요 없다 |

예시를 나열한 것만으로는 부족했고, 필요한 것은 **대화 위치에 대한 지시**였습니다(v0.16.5에서 보강).

```
| write.update.confirmed_blocked | ✅ 20/20 | get_today_tasks / (없음) / carry_over_tasks |
```

케이스 메시지는 **"마지막 날에 '모의고사 1회 풀기'를 추가해줘"**(CONFIRMED)입니다. 수정 도구가 없자
모델이 **이월 도구로 계획을 실제로 바꿨습니다.** 사용자가 요청한 건 "추가"인데 실행된 건 "미완료
항목의 날짜 이동" — **요청하지 않은 변경**입니다.

채점은 통과했습니다. `forbidTools`에 `update_plan_tasks`만 있고 `carry_over_tasks`는 CONFIRMED에서
정상 노출되기 때문입니다(v0.14.1). 즉 **하네스가 이걸 잡을 수 없게 설계돼 있었습니다** →
v0.16.5에서 `avoidTools` 범주를 만들어 측정 대상으로 승격했습니다.

### 하네스 자체에 대해 알게 된 것

`실행됨 = 시도 ∩ 노출`이므로 **금지 도구가 실행되려면 노출돼 있어야 합니다.** 데이터셋은 노출되지
않는 도구만 금지해 왔으므로:

> **`permissionBreached` 가드는 모델이 아무리 시도해도 발화하지 않습니다.**

무의미하지는 않습니다 — 누가 `AgentToolRegistry`를 잘못 고쳐 CONFIRMED에 수정 도구를 노출하면
발화합니다. 즉 **"권한 표가 깨지면 울리는 회귀 가드"**이고, 발화하지 않는 것이 정상입니다. 문서의
"금지 도구가 실행되면"이라는 표현이 이 성질을 흐렸으므로 [EVAL.md 3절](EVAL.md)에서 정정했습니다.

### 그 외 확정된 것

- **환각 도구 3종을 처음 관측**했습니다 — `add_day`, `add_task`(`write.update.completed_blocked` #8),
  `get_plan`(`write.carryover.completed_blocked` #17). 모델이 없는 함수를 발명했고 레지스트리가
  막았습니다(경고 2건). v0.15.0에 "2차 방어"라고 써 둔 것의 **첫 실측 사례**입니다.
- **"배회"는 실재합니다 — 4절의 제 판단을 정정합니다.** `write.update.completed_blocked`가 20회에서
  **도구 조합 9가지 · 1.6왕복/회**(다른 blocked 케이스 1.1)입니다. 반복 3~5회로는 변동으로 보였던
  것이 20회에서 재현됐습니다. COMPLETED에서 수정 도구가 없으면 모델이 읽기 도구를 순회하고 환각
  도구까지 부릅니다.
- **`injection.via_chat`이 20/20 `(없음)`** — 기저에서는 읽기 도구를 부른 회차가 있었는데 이제 도구
  호출이 0회입니다. 사교적 턴 억제가 인젝션 방어에도 도움이 된 것으로 보입니다(부수 효과).
- **비용은 여전히 안정적입니다** — 실행당 **1.78왕복** · 2,990토큰 · $0.00104(기저 1.83/1.77/1.79).
  입력:출력 = 986,878 : 29,684 ≈ **33:1**.

### 시간이 다음 병목이었습니다

604회 업스트림 호출 × 약 8초 = **80분**. 재측정을 반복할 수 없는 속도라, v0.16.4에서
`-Deval.threads=N`을 넣었습니다(4스레드면 20분).

## 9. 다음 실행 — v0.16.5 재측정

v0.16.5에서 **프롬프트 두 곳**을 고쳤고(요청받지 않은 변경 금지 · 인사 규칙을 위치 기반으로),
**`avoidTools` 채점**을 넣었습니다. 재측정할 것은 셋입니다.

```bash
git pull   # v0.16.5 (avoidTools + 프롬프트 + threads)
cd backend
OPENROUTER_API_KEY=... ./gradlew evalAgent -Deval.only=notool,read.today,write.update -Deval.repeats=20 -Deval.threads=4
```

`notool` 2 + `read.today` 3 + `write.update` 3 = 8케이스 × 20회 = 160회. 4스레드로 약 **12분**,
비용 약 $0.17입니다.

| 관측 | 해석 |
| :--- | :--- |
| `write.update.confirmed_blocked` 20/20 | **이월 우회가 사라졌다** — 프롬프트 규칙이 먹혔다 |
| 같은 케이스에 "요청에 없는 변경" 실패 | 규칙이 부족하다 → 도구 결과 `note`나 스키마 설명까지 손본다 |
| `notool.*` 40회 중 실패 0~1 | 위치 기반 문구가 먹혔다(기저 9.1%, 직전 5.0%) |
| `read.today.after_greeting` 20/20 유지 | 억제 과잉 없음 — 깨지면 되돌린다 |
| `write.update.draft` 20/20 유지 | 변경 금지 규칙이 **정상 수정까지 막지 않았는가** ← 새 감시 지점 |

마지막 줄이 이번에 새로 필요해진 감시입니다. "요청받지 않은 변경 금지"가 과하게 작동하면 DRAFT의
정상적인 수정 요청까지 거절할 수 있습니다 — 억제와 과잉억제는 늘 같이 봅니다.

**분모 주의**: 이번 기록의 4차(340회)는 17케이스 전체이고, 위 명령은 8케이스 부분집합입니다.
리포트 제목에 `(only=…)`가 붙으니 총계를 직접 비교하지 말고 **케이스별로** 비교하세요.
