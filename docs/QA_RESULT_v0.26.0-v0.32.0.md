## 3. 자동 테스트 게이트 — 그리고 43건의 공백

```
$ ./gradlew test
BUILD SUCCESSFUL in 1m 37s
→ 67 클래스 · 515 테스트 · 실패 0 · 오류 0 · 스킵 43
```

스킵 43건은 **전부 PostgreSQL 통합 테스트**다. `AbstractPostgresIntegrationTest`가
`@Testcontainers(disabledWithoutDocker = true)`이고 이 컨테이너에 Docker 데몬이 없다
(`/var/run/docker.sock` 부재).

| 스킵된 IT 클래스 | 건수 |
| :--- | ---: |
| `JdbcPlanRepositoryIT` | 13 |
| `JdbcPointLedgerIT` | 5 |
| `JdbcAuditEventRepositoryIT` · `JdbcKnowledgeRepositoryIT` | 각 4 |
| `JdbcAuthRepositoryIT` · `JdbcReflectionRepositoryIT` · `JdbcPlanDepositIT` · `ChallengeAutoGenerationIT` | 각 3 |
| `ChallengeJoinConcurrencyIT` · `ChallengeSettlementConcurrencyIT` | 각 2 |
| `PersistenceRestartIT` | 1 |

**이 공백이 이번 점검의 설계를 정했다.** 스킵된 43건이 겨냥하는 것은 정확히 JDBC 구현 경로인데,
그 경로에서만 드러나는 함정이 v0.32.0 개발 중 실제로 셋 나왔다(CONCURRENCY 11장). 그래서

5~8절이 그 기록이다.

> **단, "이 컨테이너에서 스킵된다"와 "어디서도 돌지 않는다"는 다르다.** 이 문서 초판은 후자로
> 적었는데 **사실이 아니었다** — 아래 3-1절이 실측이다.

## 3-1. GitHub Actions CI는 이 43건을 돌리고 있었다 — 그리고 red다

`.github/workflows/ci.yml`의 백엔드 잡은 `ubuntu-latest`에서 `./gradlew build`를 돌리고,
**GitHub 호스티드 러너에는 Docker가 설치돼 있다.** 따라서 `disabledWithoutDocker`가 발동하지
않고 PostgreSQL IT 43건이 **매 PR·매 main 푸시마다 실제로 실행된다.**

실행 이력을 조회한 결과:

| | 값 |
| :--- | :--- |
| 마지막 green | run **190** (`c65d1aa`) |
| 이후 | run 191 ~ 216 — **26회 연속 failure** |
| 걸친 릴리스 | **v0.25.0 ~ v0.32.0 (8개)** |
| 최신 main(`58f18d0`) | `515 tests completed, 2 failed` |

실패하는 2건은 **동시성 IT가 아니다**(`ChallengeJoinConcurrencyIT`·`ChallengeSettlementConcurrencyIT`는
26회 내내 **통과**했다). 실패는 다음 2건이고, 둘 다 **테스트 픽스처가 낡은 것**이다:

| 실패 테스트 | 최초 실패 | 원인 |
| :--- | :--- | :--- |
| `ChallengeAutoGenerationIT.정원이_차면_같은_조건의_다음_챌린지가_열린다` | run 191 (v0.25.0) | v0.25.0이 참가 전제조건(같은 조건의 CONFIRMED 계획 필요)을 추가했는데 이 픽스처는 `guest-filler-*`의 계획을 만들지 않는다 → `CHALLENGE_PLAN_REQUIRED` |
| `JdbcPointLedgerIT.참가와_정산을_거친_뒤에도_계정별_합계가_잔액과_같다` | v0.31.0 (이 테스트 신설 시점) | `join(id, OWNER, ..., 1L)`이 `plan_id=1`을 하드코딩하는데 `plans`에 그 행이 없다 → FK 위반 `challenge_participants_plan_id_fkey` |

**둘 다 프로덕션 코드의 결함이 아니라 테스트 쪽 결함이다.** 5~8절에서 실서버로 확인한 불변식은
그대로 성립한다. 그러나 **게이트가 빨간 상태로 8개 릴리스가 지나갔다** — 이것이 이번 점검에서
나온 가장 중요한 발견이고, QA_RESULT 공백(이 문서가 메우려던 것)과 같은 뿌리다: 아무도
보지 않는 신호는 결국 꺼진 신호와 같다.

> **왜 로컬은 green인가.** 이 컨테이너에서는 그 2건이 스킵되므로 `실패 0`이 나온다. 스킵이
> 초록으로 보이는 것이 정확히 이 공백을 8개 릴리스 동안 숨긴 구조다.

## 6. F-40 — LLM 일일 상한 2층 (v0.30.0)

`AI_DAILY_CALLS_PER_OWNER=2` · `AI_DAILY_CALLS_GLOBAL=3`으로 재기동(카운터는 인메모리라 기동 시 0)
후, **두 층을 구분할 수 있는 순서**로 측정했다.

| 순서 | 소유자 카운터 | 전역 카운터 | 응답 메시지 | 어느 층이 발화했나 |
| :--- | :--- | :--- | :--- | :--- |
| A 1회 | 1/2 | 1/3 | "AI 응답을 가져오지 못했습니다" | (통과 — 업스트림 실패) |
| A 2회 | 2/2 | 2/3 | "AI 응답을 가져오지 못했습니다" | (통과 — 업스트림 실패) |
| A 3회 | **3 > 2** | 소모 안 됨 | **"오늘 AI 사용량 한도를 모두 썼습니다"** | **소유자 층** |
| B 1회 | 1/2 | 3/3 | "AI 응답을 가져오지 못했습니다" | (통과 — 소유자 카운터 독립 확인) |
| B 2회 | 2/2 (여유) | **4 > 3** | **"오늘 AI 사용량 한도를 모두 썼습니다"** | **전역 층** |

**B 2회가 이 측정의 핵심이다.** B 자신의 소유자 한도는 아직 남아 있는데도 막혔다 — 소유자 층만으로는
막히지 않는 경로를 **전역 층이 잡는다**는 설계가 그대로 관측됐다. 로그가 어느 층인지 확정해 준다:

```
WARN c.d.b.domain.ai.client.OpenRouterClient : ai.ratelimit blocked scope=global site=agent.turn used=3 limit=3
WARN c.d.b.domain.ai.service.AgentRunner     : Agent loop failed: AI_DAILY_LIMIT_EXCEEDED
```

A 3회에는 이 `scope=global` 줄이 **없다** — 소유자 층에서 끊겨 업스트림 클라이언트까지 가지 않았다는
증거다(두 층이 세는 단위가 다르다는 설계와 일치).

### 오프사이트 백업 훅

| 점검 | 결과 |
| :--- | :--- |

두 번째가 v0.31.0에서 가장 깨지기 쉬운 지점이었다(지갑 지연 생성이 조회마다 발행하면 10줄이 된다).
`ON CONFLICT DO NOTHING`이 1행을 돌려줄 때만 기표하는 설계가 실측으로 확인됐다.

| 점검 | 결과 |

마지막 항목이 v0.32.0 개발 중 실제로 났던 버그의 회귀 점검이다(인메모리에 롤백이 없어
"돈은 안 냈는데 예치는 걸린" 행이 남았던 사례). JDBC 경로에서도 고아 행이 없음을 확인했다.

### 정산 4경로 — 전부 같은 규칙으로

| 경로 | 조건 | 환급 | 소각 | 잔액 | 결과 |
| :--- | :--- | ---: | ---: | ---: | :--- |
| ① 완주 종결 | 10/10, 예치 200P | **200P** | 0 | 1,100 | ✅ 전액 + 보상 100P 동시 |
| ② 부분 종결 | 3/4, 예치 200P | **150P** | 50P | 950 | ✅ 75% 비례, 보상 없음 |
| ③ 중단 종결 | 1/4, 예치 100P | **25P** | 75P | 925 | ✅ 포인트가 잠기지 않는다 |
| ④ **계획 삭제** | 2/4, 예치 100P | **50P** | 50P | 950 | ✅ **정산이 삭제보다 먼저** |

④가 이 릴리스에서 가장 비싼 교훈이었다. JDBC는 `plans` 삭제가 `plan_deposits`를 CASCADE로
지우므로, 삭제 뒤에 정산하면 근거가 이미 사라져 포인트가 예치 계정에 영구히 갇힌다. 순서를
뒤집은 수정이 **실제 PostgreSQL에서** 동작함을 확인했다 — 인메모리 테스트로는 볼 수 없는 축이다.

### 원장 불변식 — 모든 경로를 돌린 뒤

```sql
SELECT sum(amount) FROM point_ledger;                        -- → 0
-- 어긋난 계정
SELECT w.owner, w.balance, COALESCE(l.sum,0) FROM point_wallets w
  LEFT JOIN (SELECT account, sum(amount) FROM point_ledger GROUP BY account) l
    ON l.account = w.owner WHERE w.balance <> COALESCE(l.sum,0);   -- → 0행
-- 정산된 계획의 예치 계정 잔여
SELECT l.account, sum(l.amount) FROM point_ledger l
  JOIN plan_deposits d ON l.account = 'escrow:plan:'||d.plan_id
 WHERE d.settled_at IS NOT NULL GROUP BY l.account HAVING sum(l.amount) <> 0;  -- → 0행
```

세 쿼리 전부 기대값. 계정별 집계가 산술적으로도 닫힌다:

| 계정 | 합계 | 검산 |
| :--- | ---: | :--- |
| `system:issuance` | **−9,240** | 지갑 9개 × 1,000 = 9,000 + 보상 140 + 100 = **9,240** ✅ |
| `system:burn` | **+175** | 소각 50(②) + 75(③) + 50(④) = **175** ✅ |
| `escrow:plan:7·8·9·10` | **0** | 정산 완료 → 환급·소각이 모두 빠져나감 ✅ |
| `escrow:plan:3·4·5` | 200·400·500 | **미정산** 예치금 — 0이 아닌 것이 정상 |

### 이중 발행 없음

모든 `tx_key`가 **정확히 2행**(복식부기 두 줄)이다. 4행이면 이중 발행이다.

| kind | 서로 다른 키 | 총 행 | 판정 |
| :--- | ---: | ---: | :--- |
| `SIGNUP_BONUS` | 9 | 18 | ✅ 키당 2행 |
| `PLAN_DEPOSIT` | 7 | 14 | ✅ |
| `PLAN_DEPOSIT_REFUND` | 4 | 8 | ✅ |
| `PLAN_DEPOSIT_FORFEIT` | 3 | 6 | ✅ |
| `PLAN_COMPLETION_REWARD` | 2 | 4 | ✅ |

## 11. 관측과 남은 관찰 지점

1. **소급 점검은 릴리스 게이트를 대체하지 않는다.** 이번 26건은 현재 빌드의 동작을 확인했을 뿐,
   v0.26.0~v0.32.0 각 시점의 상태는 영구히 측정 불가다. v0.33.0부터 릴리스 시점 게이트로 복귀한다.
2. **CI가 8개 릴리스 동안 red였다 — 이 문서의 가장 중요한 발견**(3-1절). 조치는 작다(테스트
   픽스처 2곳) 지만, 발견이 늦은 이유는 작지 않다: 로컬에서는 그 2건이 **스킵되어 초록으로
   보였다.** "스킵은 통과가 아니다"를 게이트가 말해 주지 않았다. 다음 릴리스 전에 ① 픽스처
   2곳을 고쳐 main을 green으로 되돌리고, ② 스킵 건수를 리포트에 노출할지(또는 CI에서 스킵을
   실패로 볼지) 판단한다.
   한편 **동시성 IT 대조군은 실제로 26회 내내 CI에서 통과하고 있었다** — v0.25.0 문서가 남긴
   관찰 지점은 이미 닫혀 있었고, 이 문서 초판의 "한 번도 돌지 않았다"는 **오판이었다.**
3. **평가 축 공백이 3개 릴리스에 걸쳐 있다**(F-37·F-38·F-39). 프롬프트를 손대는 날이 오면
   그 전에 기저를 떠야 한다는 규칙(CLAUDE.md)이 있는데, 지금은 기저 자체가 없다 — 즉
   **슬랙 의도 파서와 자료 검색의 프롬프트는 현재 근거 없이 수정할 수 없는 상태**다.
4. **mock 폴백이 상한 측정을 가린다.** 6절에서 비스트리밍 경로의 429를 못 본 이유가 그것이다.
   운영에서는 키가 있으니 문제가 아니지만, **키 없는 환경에서 상한을 전수 점검할 방법은 없다** —
   테스트 전용 스위치를 둘지는 필요해질 때 판단한다(지금은 과잉).
5. **예치 계정 잔여 쿼리가 유용했다.** 미정산 계정(3·4·5)과 정산된 계정(7~10)이 한 쿼리에서
   구분돼 보인다 — 운영 점검에서 "0이 아닌 예치 계정"을 볼 때 **미정산인지 버그인지**를
   `plan_deposits.settled_at` 조인이 갈라 준다. OPERATIONS 2-6장의 쿼리가 의도대로 작동했다.
