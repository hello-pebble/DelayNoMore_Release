## 2. "진행"을 다루는 도구 3종의 변별이 성립했다

이번 릴리스의 최대 리스크는 유사 도구의 혼동이었다 — `get_weekly_summary`(주간)·
`get_progress`(전체 스냅샷, v0.24.0)·`get_challenge_status`(챌린지 순위, 신설)는 셋 다
"얼마나 했는가"를 다룬다. 같은 실행 안에서 셋이 각자 제 질문으로 갔다:

| 케이스 | 질문 | 호출한 도구 |
| :--- | :--- | :--- |
| `read.weekly` | "이번 주에 얼마나 했는지" | `get_weekly_summary` ✅ |
| `read.progress` | "전체적으로 어디까지 왔어?" | `get_progress` ✅ |
| `read.challenge` (신설) | "챌린지에서 지금 몇 등이야?" | `get_challenge_status` ✅ |

1회 관측이므로 "혼동률 0"이 아니라 "명백한 오배선 없음"으로 읽는다(v0.24.0 문서와 같은 기준).

## 3. 회귀 없음 + 관측 하나

- 기존 read/write/notool/injection 전 축 통과. `*_blocked` 4건과 인젝션 2건은 금지 도구 시도
  자체가 없었고(왕복 1로 종료), `notool.*` 3건도 도구 없이 종료.
- **관측**: `read.combined`(주간 성과 보고 + 분량 추천)가 기대 2종에 `get_reflection_history`를
  곁들여 3종을 불렀다. 채점상 통과(expectTools는 포함 판정)이고 근거를 더 모은 정상 행동이지만,
  도구가 늘수록 "관련 도구를 다 불러보는" 성향의 비용이 커질 수 있다 — v0.16.0 문서 4절에서
  관측된 성향의 연장이고, 반복 실행에서 빈도가 오르면 그때 프롬프트/설명문을 손댄다(기준 선행).

## 4. 남은 관찰 지점

1. **`read.challenge` 축의 반복 측정** — 표본 1. 도구 설명을 손대는 날이 오면 그 전에
   `-Deval.only=read.challenge,read.progress,read.weekly -Deval.repeats=20`으로 기저를 뜬다.
2. **도구 수와 read.combined 비용** — 3절의 관측. 도구를 더 늘릴 때(사진 인증 등) 함께 본다.
3. **정산·동시성은 이 게이트 밖** — 완주 분배·환불·이중 정산 방지는 단위·동시성 테스트가
   게이트다(F-35). `ChallengeSettlementConcurrencyIT`(naive 이중지급 대조군)는 로컬 Docker 29 ↔
   Testcontainers 1.20.4 비호환으로 스킵되므로 CI/호환 환경에서 돌린다.
